B. The fix for finding #1 — Notification Preview & Confirmation Flow

This directly answers "when I click on something it shows sent, but doesn't show what message was sent before sending." The send action must become a two-step flow everywhere in the app, not a one-click fire.

StepWhat the user sees
1. Compose (automatic)System renders the exact message per recipient using the real template + real merged data (parent name, student name, amount, date, class — whatever the template calls for)
2. Preview (mandatory, cannot be skipped)A preview panel shows: the rendered message text exactly as it will be sent, the channel(s) selected, the exact recipient list (names, not just a count like "2 defaulters"), and for bulk sends, a way to expand and see each individual recipient's rendered message — not just one generic template shown once
3. Edit (optional)User can edit the message text for this send only, or edit the underlying template for future sends
4. Confirm and sendExplicit "Send" button separate from "Preview" — this is the only action that actually dispatches
5. TrackStatus updates in place from queued → sent → delivered → read/failed per recipient, visible without leaving the screen (not just a static "sent" pill)
Non-negotiable rule for GLM 5.2: no button anywhere in the app may trigger an outbound parent/teacher/student notification without the user having seen the exact rendered message text first. If a "Send via WhatsApp" button currently calls the send function directly, it must be refactored to call a preview function first, with send gated behind explicit confirmation.

D. Rebuilding the actual ERP flow — how information should move between modules

This is the "how does the ERP actually work end to end, and how is it interlinked with the whole student biodata" part of your question. Below is the concrete data flow GLM 5.2 should implement, using the exact modules you have.

StepFlow
1Front Desk logs an enquiry → creates an Admissions lead (not a separate disconnected record)
2Admissions approval creates one Student Biodata Core record — this is the single source of truth every other module reads from and writes back to (name, DOB, class, guardian contacts, documents, medical notes, etc.)
3Fees, Attendance, Academics/Exams, Transport, and HRMS/Staff (via class assignment) all read the same biodata record rather than each module holding its own separate copy of "who this student is" — this is what "interlinked with the whole biodata" actually requires structurally
4Any module that needs to notify a parent/teacher/student routes through the single Notification Preview & Confirmation Layer (Section B) — no module sends directly
